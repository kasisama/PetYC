# QQ 宠物项目全量审查与重建路线

> 审查日期：2026-08-21
> 审查范围：项目索引、玩法模型、命令路由、数据库、QQ 官方机器人、OneBot、后台 API、后台页面、玩家可见文本、测试与发布安全
> 当前前提：项目尚未上线，不需要兼容或迁移生产数据

## 一、执行结论

当前项目不是单纯的“功能不完整”，而是同时存在两套互相竞争的产品：

1. 旧版宠物养成：宠物属性、签到、背包、商店、互动、学习、锻炼、打工、钓鱼、战斗、抽奖、交易和家族。
2. 新版远征生态：全局账号、跨平台身份、宠物档案、固定远征、图鉴、社区、小队、首领、求助和赛季。

两套系统都被编译和注册，但使用不同的数据表、命令路由和玩法规则。结果是：

- 同一个命令可能先被新版截获，再也到不了旧版。
- 玩家在新版领养后，旧版商店、改名、治疗等功能仍会判断“没有宠物”。
- OneBot 尚有旧版回退，QQ 官方机器人完全没有旧版回退。
- 后台同时展示和操作两套存档，统计口径不一致。
- 大量后台配置只在旧版生效，或者根本没有接入运行时。
- 玩家看到的部分回复是开发说明、迁移说明和平台策略，不是产品文案。

因此不建议继续在现有双系统上逐点补丁。推荐目标是：

> 以旧版熟悉的命令与养成玩法作为玩家产品契约，以新版 PlayerAccount、PlayerIdentity、PetProfile、GlobalInventoryItem 为唯一底层模型；远征和社区作为增量玩法保留，不再替代签到、商店、喂养、成长等核心循环。

由于项目尚未上线，可以直接重置本地数据库和种子数据，不建设兼容层，不保留双写，不做历史迁移。

## 三、当前真实运行链路

~~~text
OneBot 消息
  ├─ 群开关检查
  ├─ 新版统一路由
  │    └─ PetProfile / GlobalInventoryItem / Expedition / Community
  └─ 未命中时，仅群消息回退到旧版路由
       └─ UserPet / BackpackItem / Family / 旧商店与互动

QQ 官方消息
  ├─ Gateway 事件映射
  └─ 新版统一路由
       └─ 没有旧版回退，也没有旧版群开关
~~~

关键证据：

- features/init.go 同时导入 core_game、entertainment、expedition、family。
- core/websocket.go:237 先执行新版 routeOneBotMessage，命中后在 249 行直接返回。
- core/websocket.go:258 只有新版未命中时才执行旧版 RouteMessage。
- qqofficial/gateway.go:50 直接绑定 core.RouteInbound，没有旧版 RouteMessage。
- features/core_game、features/entertainment、features/family 仍注册大量旧版处理器。
- features/expedition/commands.go 又注册相同或相近的基础命令。

本地数据库也已经同时出现两套存档表中的真实数据，说明这不是理论风险，而是当前运行状态。

## 四、P0：必须先解决的问题

### P0-1 两套宠物模型和命令路由互相冲突

旧版核心表：

- UserPet
- BackpackItem
- Family
- 旧交易、工作、抽奖和互动状态

新版核心表：

- PlayerAccount
- PlayerIdentity
- PetProfile
- GlobalInventoryItem
- ExpeditionRun
- Community

新版领养写 PetProfile，旧版商店、改名、治疗等读取 UserPet。继续运行会产生：

- 玩家明明有宠物，部分功能却提示没有宠物。
- 新旧背包物品互不可见。
- 后台玩家总数、宠物数、资产数不一致。
- 删除或补发操作可能只作用于其中一套存档。
- QQ 官方和 OneBot 的功能集合不同。

处理要求：

- 只保留一个统一路由。
- 只保留一套玩家、宠物和背包表。
- 旧玩法逐项移植到统一模型，而不是继续调用旧处理器。
- 数据库直接重建，不增加临时双写。

### P0-2 玩家产品契约被擅自替换

功能说明文档仍承诺：

- 领养、我的宠物、改名、签到、背包、放生、治疗、找回。
- 商店、购买、出售、物品效果。
- 洗澡、摸头、散步、送礼、喂养、猜拳、钓鱼。
- 学习、锻炼、健身、打工。
- 战斗、抽奖、交易、家族。

但 features/expedition/commands.go:63 和 core/platform.go:270 将其中大量命令标为退休，回复“已经下线”或“升级为远征”。

这不是命令别名问题，而是产品功能被替换。目标应改为：

- 恢复熟悉命令为主入口：宠物菜单、菜单、领养宠物、我的宠物、签到、我的背包。
- 状态、今日只做兼容别名，不出现在新手引导、菜单或成功回复里。
- 旧版玩法恢复到统一模型；若确实决定删除某玩法，应先做明确产品决策，不能用一条“已升级”文案代替。
- 远征、图鉴、社区、小队、首领作为新增模块出现在二级菜单。

### P0-3 QQ 官方机器人能力与后台承诺不一致

发现：

- QQ 官方只走新版路由，旧版玩法不可用。
- GroupSwitch 只在 OneBot 链路检查，后台群开关不能控制 QQ 官方群。
- Gateway 订阅 GroupAndC2C intent，但 MapDispatch 没有处理 C2C_MESSAGE_CREATE。
- QQ 官方图片只处理官方群，频道消息没有同等图片路径。
- 一条带图片的回复会发送媒体消息和文本消息，但限流只在入口等待一次。
- 后台“关闭能力自动回退纯文本，不影响核心玩法”的描述过度承诺。

处理要求：

- 群开关前移到统一 Inbound 路由，对所有平台生效。
- 建立平台能力矩阵并在路由前校验，不让后台展示不存在的能力。
- 明确支持或关闭 C2C；订阅和事件映射必须一致。
- 图片、Markdown、键盘、互动分别建立 capability adapter。
- 每一次外部发送都单独计入限流和队列。

### P0-4 QQ 图片上传当前存在真实失败

当前控制台错误：

> 宠物图片上传失败，已降级为纯文本: QQ 图片预上传返回无效分片 1

错误来自 qqofficial/media.go:121-124。代码把“分片 URL 为空”或“本地已覆盖全部字节但接口仍返回分片”统一判定为无效分片，说明实现与 QQ 当前预上传响应契约没有完全对齐。

同时还存在：

- 本地文件优先走复杂的分片预上传，而配置 ImageHost 后可以走 URL 上传，两条路径行为不同。
- 图片失败只记日志，后台最近错误和玩家侧状态缺乏可诊断信息。
- 图片和正文拆成两条消息，需正确管理 msg_seq 和发送频率。

最小修复方向：

1. 为真实 upload_prepare 响应添加脱敏结构化日志和契约测试。
2. 区分有效数据分片、零长度终止项和缺失 URL 的异常项。
3. 按 QQ 接口返回的 index、block_size 和实际数据长度验证，不按循环位置猜测。
4. 增加单分片、多分片、末尾空项、无 parts、重复 index、超大文件测试。
5. 图片发送失败写入平台状态，后台显示错误阶段和时间。
6. 若配置了可公网访问的 ImageHost，优先使用 URL 媒体上传以降低本地分片协议复杂度。

### P0-5 默认后台暴露面过大

安全现状中做得较好的部分：

- 密码使用 bcrypt。
- 会话令牌只存摘要。
- Cookie 为 HttpOnly、SameSite Strict，HTTPS 时启用 Secure。
- 修改密码后会撤销全部会话。
- 危险操作有审计和文字确认。

高风险项：

- security/credentials.go:21 默认管理员密码为 123456。
- security/runtime_config.go:120-122 默认监听 0.0.0.0。
- 登录接口没有限速、失败锁定或渐进延迟。
- 初次启动不会强制修改默认密码。

处理要求：

- 默认监听 127.0.0.1。
- 首次启动生成一次性随机管理员密码，或强制初始化向导设置密码。
- 发现默认密码时禁止进入后台业务页。
- 登录加入 IP 与账号双维度限速。
- 高风险写接口增加 Origin 校验；SameSite 继续保留。

### P0-6 并发约束不足

远征：

- StartExpedition 先 Count 再 Create。
- ExpeditionRun 只有普通 account_id + status 索引，没有“一名玩家最多一个 running”约束。
- 并发消息可同时通过检查并创建两条进行中远征。

求助：

- SupportHelpRequest 读取 Fulfilled，扣除物品，再用绝对值写回 newFulfilled。
- 并发支援可能覆盖进度，或在边界处超额支援。

处理要求：

- 在数据库层增加可执行的唯一性或锁定策略。
- 使用条件更新：仅当 remaining 足够时原子递增。
- 以 RowsAffected 判断竞争结果。
- 增加并发回归测试，不只测试顺序调用。

## 五、P1：玩法与数据一致性

### 5.1 新版宠物成长字段大多没有形成循环

PetProfile 当前字段包括 Mood、Readiness、Affection、Growth、BondLevel、Traits、Skills。

实际行为：

- BondLevel 初始化为 1，未找到升级逻辑，但状态页和后台把它当成长指标展示。
- Readiness 通过签到和部分互动不断增加，远征不消耗。
- Mood 在领养和签到时写入，缺乏自然变化或玩法影响。
- Affection 主要由签到增加。
- Traits 有行为累积逻辑，是实际生效项。
- Skills 根据定位直接全部获得，没有学习或成长过程。

建议：

- 明确每个展示字段的来源、变化、消耗和用途。
- 没有实际规则的字段先不展示。
- 羁绊等级由累计好感或陪伴经验计算，并有明确升级反馈。
- 准备度成为远征和活动资源，出发消耗、休息和照料恢复。
- 心情影响有限且可解释的结果，不做不可见随机惩罚。
- 技能需要满足成长或任务条件，而不是切换定位后立即全部掌握。

### 5.2 远征配置硬编码

features/expedition/service.go:54-58 固定了三档远征：

| 档位 | 时长 | 奖励 |
|---|---:|---|
| 林间巡查 | 10 分钟 | 林地样本、调查记录、成长、图鉴 |
| 遗迹调查 | 2 小时 | 古代零件、调查记录、成长、图鉴 |
| 深层生态勘察 | 8 小时 | 生态样本、调查记录、成长、图鉴 |

后台无法把一次远征作为完整对象配置。活动、图鉴和奖励轨道看似可编辑，但远征结算并不读取这些奖励配置。

建议建立 ExpeditionTemplate：

- 名称、区域、时长、准备度消耗。
- 解锁条件、推荐属性、姿态影响。
- 固定奖励、可选奖励、图鉴进度。
- 开始图、进行中图、完成图。
- 启用状态和排序。

出发时保存奖励快照，结算只读快照，避免运营中途改配置影响已出发任务。

### 5.3 物品和经济没有闭环

新版远征把材料写入 GlobalInventoryItem，但旧商店、物品效果、购买、出售仍使用旧背包和 UserPet。

结果：

- 新版玩家获得物品后，缺少消费和使用入口。
- 物品配置中的 Effect、RewardType、OpenReq、Time 等主要为旧版服务。
- 社区共建、首领和求助成为少数消耗口，无法替代完整商店和养成经济。

目标闭环：

~~~text
签到 / 互动 / 远征 / 活动
  → 货币、材料、食物、礼物、训练道具
  → 商店 / 使用 / 喂养 / 送礼 / 训练 / 进化
  → 属性、羁绊、外观、图鉴与新活动解锁
~~~

## 六、P1：玩家命令与文案

### 6.1 当前文案的核心问题

用户指出的“奖励采用固定进度，不含抽奖”是典型问题：它向玩家解释开发策略，而不是描写正在发生的游戏。

同类问题还有：

- “这是限额赠礼，不开放自由交易。”
- “小队玩法为异步协作，不设置强制考勤。”
- “平台额度不足时仍只在你主动查询后回复。”
- “新版不会永久失去宠物。”
- “该对抗或随机玩法已经下线。”
- “旧钓鱼玩法已升级为……”
- “家族已经升级为……”
- “内部账号：UUID。”
- “固定材料”“低压力”“自动结算”等产品设计术语。

旧版还会直接向玩家发送：

- 系统错误、数据库错误、数据库保存失败。
- 数据类型错误，请去控制台修改。
- 带完整底层错误的 err.Error。
- “请联系管理员”式无行动价值提示。

语气也不统一：

- 旧版大量使用“阁下”、训斥、羞耻或威胁表达。
- 新版使用平静的同行、探索和社区表达。
- 标点、括号、引号、加号、Emoji 和数字单位没有统一规范。

### 6.2 文案真实性问题

- 签到回复写“羁绊经验 ×1”，代码实际增加 affection、readiness、mood，并发放陪伴印记。
- “滚动七日记录”实际只是最近七天记录数量，不是连续签到。
- “失败仍会获得基础调查进度”，当前远征没有失败分支。
- “主动通知已开启”，当前只有偏好开关，没有主动发送调度器。
- “命令执行健康度”把处理器 err == nil 当成功；大多数业务失败被处理成友好文本并返回 nil，因此后台成功率不等于玩法成功率。

### 6.3 建议的玩家文案规范

每条回复最多完成四件事：

1. 结果：发生了什么。
2. 变化：获得、消耗或状态变化。
3. 氛围：一小句符合宠物世界观的反馈。
4. 下一步：只推荐一到两个真实可用命令。

禁止出现在玩家侧的词：

- 新版、旧版、下线、迁移、固定进度、不含抽奖。
- 平台额度、接口、数据库、内部账号、UUID、配置未加载。
- 限额策略、强制考勤、低压力设计、自动结算策略。
- 原始 err.Error 和 SQL/HTTP 细节。

错误分层：

| 层级 | 玩家回复 | 控制台/后台 |
|---|---|---|
| 输入错误 | 告诉正确格式并给例子 | 记录命令与错误码 |
| 业务条件不满足 | 告诉缺少什么和如何补齐 | 记录业务错误码 |
| 平台失败 | 提示稍后重试，不暴露接口 | 记录 HTTP、响应码、阶段、request id |
| 数据库/程序错误 | “刚才没有处理成功，请稍后再试” | 完整结构化错误与堆栈 |

### 6.4 重点文案替换示例

## 七、P1：后台 API 与信息架构

### 7.1 新旧 API 并存

admin/handler.go:77-115 明确同时注册：

- 旧 stats、pets、items/give、groups、compensation、configs 接口。
- 新 overview、players、expeditions、communities、content、platforms 接口。

旧 GetStats 统计 UserPet，新 Overview 统计 PetProfile。后台可能同时出现两个互相矛盾的“总宠物数”。

同时存在两种响应：

- 新接口使用 HTTP 200 + code/msg/data，即使业务失败也返回 200。
- 旧接口和鉴权使用真实 HTTP 状态 + error/message。

建议：

- 删除未路由页面对应的旧 API。
- 所有接口统一 HTTP 语义：2xx 成功、4xx 输入/权限/冲突、5xx 系统错误。
- 响应统一 request_id、code、message、details。
- 前端只保留一套 unpack 和错误处理。
- OpenAPI 或至少生成式路由清单成为唯一契约。

### 7.2 图片资产存储重复

admin/handler.go:1142-1178 将同一上传文件同时写入：

- AppData 配置目录下的 图片/上传

core/app.go 又只把 ./图片 暴露为 /images。

问题：

- 产生重复文件和孤儿。
- 项目工作区被运行数据污染。
- 打包后的当前工作目录不稳定。
- 删除配置不会回收两份资产。

建议：

- 只保留 AppData/QQPET_DATA_DIR 下的单一资产目录。
- /images 直接服务该目录。

- 上传使用内容 hash 去重。
- 删除前检查引用；提供孤儿扫描与清理。

## 九、P1：指标与运营真实性

### 9.1 命令成功率定义错误

core/platform.go:140-142 使用 handler 返回的 err 是否为空作为成功标记。

但新版处理器把多数业务错误转成玩家文本，并返回 nil。例如：

- 没有宠物。
- 远征未完成。
- 物品不足。
- 输入格式错误。
- 不允许支援自己。

这些都会计为成功。后台“命令执行健康度 98%”只能说明处理器没有抛出技术错误，不能代表命令成功。

建议拆分：

- received：收到。
- matched：命中命令。
- validation_failed：格式错误。
- business_rejected：条件不满足。
- completed：业务成功。
- platform_send_failed：发送失败。
- internal_error：系统错误。

后台分别展示业务完成率和技术可用率。

### 9.2 主动通知是未实现承诺

NotificationPreference 目前只有读写和删除，没有发现定时器、任务表或发送调度器。

在实现之前：

- 后台和玩家侧不应写“远征完成通知已开启”。
- 开关应隐藏，或标为“规划中”且不可操作。

实现后需要：

- Outbox/NotificationJob。
- 幂等键。
- 平台能力和频率限制。
- 失败重试与退避。
- 用户关闭通知的实时校验。
- 后台发送记录与失败原因。

### 11.1 唯一领域模型

- 未路由旧页面。

### 11.2 唯一命令链路

~~~text
平台适配器
  → InboundEvent 标准化
  → 平台/群开关/权限/限流
  → 命令解析与参数校验
  → 统一领域服务
  → 结构化 CommandResult
  → 玩家文案渲染
  → 平台能力渲染与发送
  → 指标与审计
~~~

CommandResult 不直接携带底层错误文案，应包含：

- status：completed、validation_failed、business_rejected、internal_error。
- message_key：文案键。
- variables：宠物名、奖励、数量、下一命令。
- image_asset：图片资产 ID。
- next_actions：标准命令 ID。
- internal_error：只进入日志，不进入玩家消息。

4. 背包、物品、商店、购买和使用。
5. 喂养、送礼、洗澡、摸头、散步。
6. 学习、锻炼、健身、打工。
7. 进化和觉醒。

增量循环：

1. 远征和图鉴。
2. 社区、共建、小队、首领、求助。
3. 周期活动和奖励轨道。

高风险或强随机玩法：

- 抽奖、战斗、交易、钓鱼随机结果可以恢复，但需要明确概率、保底、次数、风控和审计。
